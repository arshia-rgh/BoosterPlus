# Coordinated recovery and erasure protection

`restore-point-drill` is implemented; real encrypted BR/TiKV restoration remains a **server qualification**, not a local pass. Never promote its result automatically. Source requirements are retained in `final-launch.md`.

## Capture and exact-point drill

1. Configure independently hosted encrypted restic and BR storage/keys as in [BACKUP.md](BACKUP.md) and [PITR.md](PITR.md). Start the log task, record its global checkpoint and take the full SQL base from the current signed release.
2. Run `make media-backup`. One TiDB snapshot fixes the SQL timestamp and complete live-media index. Capture rejects missing/corrupt files; it waits at most three minutes for continuous logs to reach that fixed timestamp. Runtime configuration/key bytes are copied privately and hashed; operator release/capture locking prevents ordinary concurrent rotation. A configuration change during upload fails the receipt. The encrypted `playora-point-v1` archive includes `/capture`, `/mail` and `/pki`. Mail is an interval copy, **not an atomic SQL-aligned mailbox snapshot**; recovered queues/indexes stay offline. No historical outbound messages are replayed.
3. Keep the exact signed release bundle, SQL master/snapshot keys and restic password independently available. Set `RESTORE_SNAPSHOT` to the full64-character archive ID, `RESTORE_TARGET` to a **new** absolute directory outside the installation, `RESTORE_ACK` to that same path, and `RELEASE_DIRECTORY` to the matching signed bundle. Run as the dedicated UID1000 operator.
4. Set `PITR_RESTORE_ENV_FILE` to a private file containing a **different read-only** S3 identity (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional region). Its tested policy allows list/read of the SQL source prefix and denies writes/deletes. Do not use the primary BR writer. Restore checkpoints go into the new target; a provider denial of an unexpected source write must fail the drill, never prompt broadening permissions.
5. If erasure has ever been enabled, also set `PRIVACY_RECOVERY_ENV_FILE` to the current dedicated journal read/list configuration described below. Run `make restore-point-drill`. It restores the archive, verifies release/schema/hash/SQL coverage, initializes fresh TLS/DB/object identities, restores only `playora.*` at the exact timestamp, verifies migration history, imports/checks every media object, invalidates sessions/challenges/recoveries and replays supplied independent privacy evidence.
6. All app/DB/object networks are internal. Only BR/TiKV reach off-host SQL storage; a separate temporary journal-export tool can reach the journal and receives only its dedicated configuration. No gateway, worker, mail daemon or customer API server is started. The API image runs only explicit CLI commands. Completion and failures retain private files and `RESTORE_QUARANTINED`; containers/networks from this unique drill are stopped without deleting volumes/files.
7. Inspect the private `point-restore.json`, rehearse business invariants with fixture data, purge eligible restored media, reconcile financial/jobs/outbox state, review conservative privacy holds and prove current evidence completeness before any separately controlled promotion. An absent journal is recorded as `privacy_replayed=false`, never privacy recovery success. Measure actual data loss and total return-to-service time, including downloads/operator work/reconciliation, against15minutes/fourhours. The script's elapsed time is only one part of full RTO.

Source: [TiDB checkpoint restore](https://docs.pingcap.com/tidb/stable/br-checkpoint-restore/) and pinned8.5.8 BR source. Matching-version table-filter/PITR, local checkpoint behavior and read-only source access must be exercised on the server. Failed/interrupted targets remain quarantined for diagnosis; this first coordinator requires a fresh target on retry and never blindly overwrites an interrupted one.

## Independent privacy journal

The API always requires a recovery journal for irreversible customer erasure. With absent/disabled configuration, erase/finalize fail closed even if an owner publishes an enabled retention policy. Requests, exports and ordinary holds remain available. An owner policy is still separately required; recovery configuration never supplies retention periods.

Use `privacy.env.example` as **private backend configuration**, not frontend settings. Configure a dedicated off-host HTTPS bucket/prefix `privacy/v1/`, separate credentials, a random256-bit hexadecimal encryption key and the deployment project identity. Keep the key under independent custody. `PRIVACY_RECOVERY_OFFHOST_CONFIRMED=true` is an operator assertion that requires real host/durability qualification; differing DNS names alone do not prove independence.

- Runtime identity: conditional create and get only; deny list/delete and overwrite (enforce the conditional-write requirement in storage policy). Records have opaque random keys and authenticated AES-GCM ciphertext bound to project/object key. No email, hold reason, messages or game credentials are stored. A write is acknowledged only after exact ciphertext readback.
- Recovery identity: list/read only. The separate `PRIVACY_RECOVERY_ENV_FILE` contains only `PRIVACY_RECOVERY_*` entries, enabled=true, the correct project, current independently held encryption key and read/list credentials. `restore-point-drill` exports/decrypt-validates all bounded evidence before applying it to isolated SQL. It does not grant the recovered API outbound access.
- Erase intent is written before the SQL erasure transaction. A failed transaction can leave a conservative intent; it never causes automatic erasure during recovery. The committed `erased_pending_files` state and confirmed eligible-file purge must already exist before finalization records an independent `erased` fact. A finalization rollback is safe because live erasure had already committed. Retries append evidence rather than replace it.
- Holds append conservative records before committing the hold. Releases do not delete historical evidence. On restore, confirmed erasures reuse the existing protected-evidence-preserving cleanup. Uncertain intents and holds suspend the affected customer and hold existing requests for owner review. Financial/dispute/proof/audit evidence remains protected. Never auto-unsuspend an account based only on a later local backup.
- Export completeness requires a fresh independent listing with no continuing source erasure writers at final promotion; the ordinary drill may run while primary writes continue and therefore cannot qualify final cutover freshness. Retain historical journal records until every relevant backup/replica is expired and holds are resolved under the approved policy. Test actual conditional writes, storage durability/replication/version retention and read-only recovery policy.
- Before enabling this on an existing installation, independently reconcile/export all previous completed/pending erasures and holds. This is not automatic historical backfill. If that evidence is unavailable, keep deletion disabled and recovery quarantined. The fresh MVP must prove there are no earlier unjournaled erasures.
- Keep this first journal key stable and escrowed. Do not replace it in place: key rotation requires a reviewed full authenticated export/re-encryption into a separate namespace, complete equality/restore verification and retention of old key material for old records. Loss of this key blocks safe privacy recovery.

Standalone backend CLI commands are `recovery-privacy-export NEW_PRIVATE_FILE` (no database access) and `recovery-privacy-replay PRIVATE_FILE` (explicit isolation acknowledgement/marker required). Archives remain mode0600, bounded, encrypted per record and operator-controlled. Never expose them as customer downloads. SQL replay deliberately does not start a purge worker or mark backup expiry complete: independently verify the isolated eligible-file purge before promotion.
