# Booster Plus deployment foundation (R04)

This directory contains deployment configuration and operator tools only. Application code, dependencies and builds remain in `backend/` and `frontend/` (including its independent admin target). R04 supports a single application host using managed TiDB and private S3-compatible storage. It does not provide high availability or public-launch approval.

## First deployment

1. Provision a Linux host with Docker Engine/Compose v2 supporting raw env files and `!override`, DNS for the site, inbound 80/443, and outbound connectivity to certificate authorities and configured integrations. Reserve a non-overlapping private IPv4 `/24` edge subnet and its upper `/25` for automatic container addresses. Place the fixed gateway IP in the lower half so it cannot collide with automatic assignments.
2. Provision managed TiDB with verified TLS and separate runtime DML and migration DDL identities. Create a private, non-public S3 bucket and credentials restricted to the `media/` prefix. Supply a real TLS SMTP service and approved account terms. For self-managed TiDB use a separately qualified PD/TiKV/TiDB cluster across appropriate failure domains; the local unistore test service is not a production database.
3. Build and scan backend, storefront/admin and the gateway (`make -C production docker-build`). Publish immutable images to your registry and record their digest references, including the existing patched scanner image. Release publishing/provenance automation belongs to R10.
4. Copy `.env.example` to a mode-0600 manifest. Set actual domain/email, image digests, gateway subnet/IP and absolute paths to three protected runtime files based on `config/*.example`. Configure `MEDIA_SCANNER_ADDRESS=/run/clamav/clamd.sock`. Runtime secrets must be different from the authentication/proxy/vault keys as required by the backend. Read `secrets/README.md`.
5. Run `make -C production preflight`, then `migrate-status`, `migrate-plan`, and explicitly `migrate-up` with the DDL identity. Existing production data requires a verified recoverable backup and compatibility review before a migration; do not use this foundation to bypass R10 release/restore qualification.
6. Run `make -C production up`, `status`, and `smoke`. Bootstrap the first owner through the protected backend CLI as described in `../docs/admin-workspace.md`, then sign in and complete both factors. There is no default staff account.

Set `DEPLOY_ENV=/absolute/path/to/manifest` to select a different protected manifest. `config-check`/`validate` inspect resolved Compose in memory and validate Caddy without printing secrets. `preflight` also checks application configuration and packaged SQL. `migrate-*` operate only the explicit Cobra CLI. `up` never applies migrations; an incompatible schema prevents API readiness. `logs` emits bounded application logs for private operator use, never resolved environment configuration. No command deletes production volumes. `release`/`rollback` now verify signed bundles and retain interrupted-operation receipts; `backup`/`backup-verify` provide encrypted cold recovery snapshots and `restore-drill` retains restored data in quarantine. These new operations require server rehearsal before production reliance. See [release](RELEASE.md), [backup](BACKUP.md), [mail](MAIL.md), [owner inputs](OWNER_REQUIREMENTS.md) and [evidence](LAUNCH_EXECUTION.md).

## Network and process boundaries

Only Caddy publishes host ports. `/admin`, `/admin/*`, and `/admin.data` reach the admin image. All other paths, including `/api`, reach storefront, which supplies the existing trusted proxy credential to the private API. Caddy strips client-supplied internal/forwarding headers and supplies the observed remote address; only its exact bridge IP is trusted by the frontend. Do not add a CDN/proxy in front without explicitly qualifying its source IP policy. API, worker, migration and scanner have separate outbound access to their required managed services. Internal edge/application networks are not public listeners.

Applications and gateway are non-root, read-only, capability-dropped, resource-bounded and gracefully stopped. Caddy's persistent certificate/config volumes are initialized with its non-root ownership by the gateway image. Scanner initialization is the documented exception: upstream requires root and a writable filesystem for signatures and then drops daemon privileges. It binds TCP only to its own loopback and exposes its Unix socket only through a dedicated volume mounted into backend processes. Socket mode permits those isolated container users to connect; no frontend or public container mounts it. Scanner signature freshness is checked before uploads are accepted.

Caddy automatic TLS persists certificates in `gateway-data`. API readiness includes schema compatibility; the worker has a read-only `dependencies ready` healthcheck and startup checks the same schema and uses the existing SQL jobs/reconciliation. Backend `boosterplus dependencies check` verifies schema readiness, scans harmless bytes, and writes/reads/deletes one random `media/checks/` object. Ambiguous writes and failed checks still attempt bounded cleanup; a cleanup failure is reported. Grant the runtime identity appropriate access for that diagnostic, or use a dedicated operator identity with the same service scope.

## Local qualification

`make -C production pre-commit` runs policy tests, builds/scans the pinned gateway and runs `staging-test`. Root `make pre-commit` includes it after both application gates. Required application images and Docker must be available; failure is not skipped.

The staging override is only for disposable local tests. It binds the gateway to random loopback ports, generates a two-day private test CA, uses verified TiDB/S3/SMTP TLS with `APP_ENV=staging`, and shares no application data with development or production. Explicit local bootstrap creates test identities before the normal SQL migration CLI runs. Test mail stays in the isolated mail catcher. No TLS-verification bypass or production credential is used. All project containers, SQL/media/certificate volumes and secret files are removed in cleanup. The separately labeled `boosterplus-qualification-signatures` volume retains only malware-definition cache across tests, with normal freshness checks; it contains no customer data.

The drill tests distinct SSR apps/deep links, trusted proxy and security headers, real email sign-in and secure cookies, CSRF/customer-vs-staff boundaries, explicit migration/schema verification, TLS object round-trip, Unix scanner access, scanner/storage outage recovery, database outage/readiness/recovery and clean API/worker shutdown. Fixtures are not public-approved prices/policies. Full browser/accessibility journeys remain in the frontend gate. Real Google/provider, clustered TiDB/load, remote DNS/TLS, backups/restore, monitoring and release qualification remain R10/R11.

Sources for the configuration: [Caddy reverse proxy and forwarding rules](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https), [TiDB TLS settings](https://docs.pingcap.com/tidb/stable/tidb-configuration-file/), and [Mailpit STARTTLS configuration](https://mailpit.axllent.org/docs/configuration/smtp/). The gateway rebuilds Caddy 2.11.4 using pinned xcaddy 0.4.7 and Go 1.27.1, with explicit patched x/crypto, x/net, x/text and gRPC versions. Its runtime removes unused curl and pins patched OpenSSL libraries; the final image still undergoes the mandatory vulnerability scan. This follows the [official custom-build workflow](https://caddyserver.com/docs/build). No public host or provider account was provisioned by this stage.
