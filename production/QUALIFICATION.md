## Fixture HTTP load workload

`make load-test` consumes private `LOAD_PLAN`, `LOAD_CA_FILE`, and a new private absolute `LOAD_REPORT`. It accepts only a loopback HTTPS origin and project `boosterplus-load-<12hex>`, with acknowledgement `isolated-fixtures-no-live-provider`. Provision a separate representative fixture deployment, isolated provider/mail/storage fixtures and exactly100 authenticated sessions first. Never tunnel production into the accepted loopback port.

Plan shape: `{origin, project, acknowledgement, sessions:[{fixture_id, steps:[{method,path,class,expected_status,headers,body}]}]}`. Steps use GET/POST `/api/v1/...`; classes are `ordinary`, `estimate`, `chat`. Private headers may contain Cookie, X-CSRF-Token, Content-Type and matching Origin. `__REQUEST_ID__` in a POST body becomes a fresh UUID. Build valid domain-specific journeys/consent/contracts from the isolated fixture setup, including reads, estimates, requests, chat sends and fixture checkout. Preserve each session's authorization and order/conversation ownership. Static invalid forms or cheap endpoints mislabeled as estimates do not qualify the workload.

The runner rotates100 distinct fixture sessions at20requests/second for five minutes, with at most one in-flight request per session. Delayed scheduling/busy sessions, HTTP failures, missing request classes and excessive latency fail acceptance. Reports contain only aggregate counts/timings; no cookies, bodies, response content or identifiers. Ordinary p95 must be below500ms and estimates below750ms. Separately measure **persisted chat visibility** within two seconds (send→other authorized reader), worker backlog drain, reconciliation/idempotency and resource usage; HTTP response latency alone is not chat delivery or full capacity qualification. Record hardware, dataset sizes and dependency latency assumptions. No load test has been run on the workstation.
