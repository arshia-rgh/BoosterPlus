# ACCOUNTS175 — PLAYORA-owned account listings and explicit inventory ownership

Owner request, 22 October 2026 (verbatim): “Currently sell account is the seller submit the playora buys from it then publish or publish and after buyer buyed pay seller. I want that the admin can publish for sell its own account, we should have these separation in the account inventory (account is ours (playora) whose that we buy from the seller are also playoras, and cant publish its owned account. implement with decision of the senior software engineer and senior ui/ux designer, nice ui/ux and also with trips to reviews (both senior software engineer review and senior ui/ux designer review)”.

## Interpretation

“cant publish its owned account” is read as “can publish its own account”. Sellers still cannot publish anything themselves; nothing here gives customers publishing ability.

1. Administrators can create and publish an account listing that PLAYORA itself owns, with no seller submission, seller agreement, seller commission, handover or payout.
2. The admin Account inventory separates ownership:
   - **PLAYORA-owned**: listings created by staff, plus listings from accepted buy-first (“buy before resale”) seller offers. PLAYORA bought those accounts; resale still waits for the confirmed seller payout, and the inventory says so when it is not confirmed yet.
   - **Seller consignment**: listings sold on the seller's behalf; the seller is paid after the buyer's delivery and inspection.

Converting an existing consignment listing into PLAYORA ownership (a buy-out) is out of scope; it needs its own seller agreement and payment.

## Decisions

The independent senior software engineer decided the model before coding (record kept privately with the side-session notes); the independent senior UI/UX designer decided the admin experience in [the design review](redesign/reviews/ACCOUNTS175_DESIGN.md) (round 0, D1–D22).

- **Data model.** `account_listings.origin` (`playora` | `buy_first` | `consignment`) is immutable and has no default. Ownership is derived, never stored: `playora`/`buy_first` → PLAYORA, `consignment` → seller. `submission_id`, `offer_id` and `seller_id` are NULL only for PLAYORA-created rows; the existing one-listing-per-submission/offer unique keys still hold for seller rows (NULLs do not collide). New index `account_inventory_origin (origin,state,id)`.
- **Migration 50 backfill.** Each existing listing takes its origin from its accepted seller offer's `model`. A listing whose offer is missing, not accepted, mismatched or has an unknown model stops the migration (security-lock duplicate key) before any DDL; ownership is never guessed.
- **Buyer price.** PLAYORA-created listings use the published buyer rule already used for every account sale (buy-first listings were already PLAYORA-owned): USD base plus an independently half-up-rounded 5% buyer commission, the seven-day (168-hour) inspection and the owner-approved buyer terms. No fee is invented or removed. The new draft carries only those approved terms; price, delivery timing, account facts and images stay empty until staff enter them.
- **No seller money.** PLAYORA-created listings never create a seller offer, commission, `payments.seller_obligation` job, seller payout or seller handover.
- **Images.** Staff upload screenshots through the existing scanned admin artwork pipeline under a new purpose, `account` (full image, gallery renditions). They are served publicly only through the release-bound account image route, never through the public artwork route or other purposes.
- **Authorization.** Administrators (and owners) create with one recent verification factor; creation is idempotent (the request key is the listing ID) and audited as `resale_playora_inventory_created` with origin and game. Editing, publication and withdrawal reuse the existing administrator endpoints and checks.
- **Public pages.** Unchanged (D22): every account is sold and supported by PLAYORA under the same buyer terms; the public projection exposes no ownership, origin or seller data.

## Implementation

- Migration `000050_account_inventory_origin.sql`; runtime schema 50; readiness checks the origin column, its index and that the three provenance columns are nullable. The migration runner refuses to step back across 50 once any PLAYORA-created listing exists.
- `backend/internal/resale/ownership.go`: `CreatePlayoraListing`, ownership/origin filters and counts, buy-first payout facts, listing-scoped readiness (`blockers`) for PLAYORA rows, account-artwork image checks. `ChangeListing`, `Reserve` (order snapshot = the game's current catalog release, as for shop orders), `CancelPaid`, reviews, privacy holds and listing image serving branch safely on missing provenance.
- New API: `POST /api/v1/admin/account-listings` (`request_key`, `game_id`, `title`); `GET /api/v1/admin/account-listings?ownership=playora|seller|origin=…&state=…` adds `counts`; listings add `origin`, `ownership`, optional `seller_payout_confirmed` and `blockers`. Publishing while a game's account sales are off returns 409 `resale_game_unavailable` with specific staff copy (previously generic `resale_conflict`).
- Privacy fix found during design: the accepted-offer erasure hold used `NOT IN (SELECT offer_id …)`; one sold or withdrawn PLAYORA listing (NULL `offer_id`) would have made it unknown for every seller and silently dropped the hold. The subquery now excludes NULLs.
- Admin UI (`frontend/app/resale/inventory.tsx`, `ownership.tsx/.css`): intro, **Add a PLAYORA account** with an inline create panel (game, public title, idempotent retry after an uncertain result, discard prompt), ownership filter links (All / PLAYORA-owned / Seller consignment, `?owner=`, server counts), Status filter (withdrawn shown as Paused), listing cards with ownership chip, source and the rule on sale, and buyer total. The editor shows an ownership panel; PLAYORA-created rows hide the seller link, seller chat images, seller summary suggestions and seller/handover/payout readiness, use staff uploads and a listing-scoped checklist, and confirm “PLAYORA owns this account”.

## Recovery note

Migration 50 adds a column and an index and relaxes three columns to nullable; existing rows only gain their derived origin. The schema50 runtime refuses schema49 and the current schema49 application refuses schema50: never restart `0be12a0` against schema50. While no PLAYORA-created listing exists, the CLI can step back over 50 without deleting rows; once any exists, the step back is refused, and recovery needs a forward fix or a separately verified pre-migration restore. Off-host recovery remains absent and production rollback is unqualified. Before activation, a SELECT-only inspector must confirm the backfill precondition count is 0 on production; otherwise stop and ask the owner.

Owner decisions flagged, none blocking: whether PLAYORA-owned listings should ever drop the separate 5% buyer commission (needs a versioned policy revision); a future buy-out flow for consignment accounts; a future owner-only pre-sale credential vault for PLAYORA inventory (today credentials are entered only at delivery through the protected delivery secret).
