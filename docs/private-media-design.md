# Private conversation images

Customers and staff can attach private images to their conversations. Order conversations inherit the order customer's access. Staff-only notes keep a separate immutable audience. An upload is visible only to its uploader before it is bound to a message; afterward, current conversation permissions apply. Another customer, an unassigned booster, or a customer guessing an internal attachment ID cannot retrieve its metadata or content.

Uploads accept JPEG, PNG, and WebP, up to 4 MiB, 4 million pixels, and 4096 pixels per dimension. WebP becomes PNG. Re-encoding strips metadata and trailing content; original filenames are neither sent to the API nor stored. Each uploader can reserve 20 unattached files, 100 MiB, and 1000 active files. Each conversation/audience is limited to 100 files and 100 MiB. Intent and byte-upload rates use the shared authenticated account/address throttle. The UI attaches one image per message; the API supports up to four.

An intent fixes the uploader, conversation, audience, byte count, SHA-256 checksum, and UUID retry key. Authenticated, CSRF-protected binary upload passes through the same-origin frontend proxy to private S3 storage. This intentionally avoids browser storage credentials and cross-origin upload configuration. Retrying can write only the identical declared bytes. Finalization atomically records the queued state and a reference-only `media.scan` job. No object key, filename, raw image, credential, or signed URL enters job payloads or application logs.

The worker verifies the stored checksum and complete byte count, streams the bounded content to ClamAV, checks decoder dimensions before allocating pixels, and writes re-encoded output to a separate clean object. Only then does a conditional update make it ready. Clean output has its own stored checksum, length, and type, checked again on download. Source storage failures, stale definitions, scanner unavailability, truncation, scan-limit errors, and unknown responses fail closed. Positive malware findings and invalid images become rejected. Exhausted jobs remain visible as `scan_failed`; a bounded retry resets only a failed job, and staff retries require recent authentication.

ClamAV 1.5.3 is pinned by digest. Its upstream image needed patched OpenSSL packages to fix CVE-2026-14456; `deploy/scanner.Dockerfile` now pins 3.5.9-r0 after Alpine superseded 3.5.8-r0, plus PCRE2 10.49-r0 for the subsequently reported scanner-library advisories. The required image gate scans the resulting image separately. Compose uses a loopback-only host port, strict scan limits, a persistent signature volume, and UTC. Definitions must be no older than 72 hours. The image currently requires AMD64 emulation on Apple Silicon. Production configuration requires a private Unix scanner socket and HTTPS object storage; the development Compose topology is not a public scanner deployment.

Binding is atomic with the message, counters, audit, and notices. A ready image can be bound once, to the original conversation and audience, by its uploader. An internal image cannot be downgraded into a public reply. Draft selection and processing block message submission until the image is ready or removed.

Downloads require both an active authorized session and a one-minute signature bound to that session and file. The API checks access before and after reading storage, serves only the clean object, and sends `no-store`, `nosniff`, `no-referrer`, and a generated attachment filename. Neither storage nor quarantine is anonymously accessible. Previously downloaded bytes cannot be recalled after revocation.

Unattached intents expire after 24 hours. Removing a draft immediately revokes access; the worker retries deletion of both namespaces. Tombstones remain eligible for repeated deletion through expiry plus one hour so bounded writes already in flight cannot leave permanent orphan objects. Cleanup rotates bounded batches and keeps failed work retryable. Bound proof is retained until the audited lifecycle policy is implemented in the fulfillment/privacy phases.

Use `make -C backend dev-up` to build and start storage/scanning, and the root `make pre-commit` to run real TiDB/storage/scanner checks plus the browser suite. Tests use unique database schemas and object prefixes in local storage; they fail if required services or credentials are missing. `make -C frontend test-e2e` also rebuilds the production frontend first. Host-run API/worker binaries require the `MEDIA_*` settings in `.env.example`; Compose wires them from local generated credentials.

This stage covers conversation images. Dedicated progress-proof records, assigned-booster access, seller submission scopes, public catalog image management, and fulfillment-stage form attachments are integrated in their dependent phases. Encrypted credential storage is separate from images and chat.
