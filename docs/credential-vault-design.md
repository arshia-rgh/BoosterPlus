# Temporary credential vault

P06 provides an internal encrypted storage primitive. It has no generic HTTP submission or reveal endpoint. P08 fulfillment and P09 resale must supply their own resource policies and screens before customers can use it. Ordinary form answers, chat messages, notifications, and events must never carry game passwords or transfer secrets.

Each bundle belongs to a canonical resource UUID, owner UUID, and explicit purpose (`game_access` or `account_transfer`). AES-256-GCM encrypts the payload using a new random data key on each write. A separate versioned master key wraps that data key. Authenticated data binds both envelopes to the bundle, resource, owner, and purpose; the wrapping envelope also binds its key version. Random nonces come from Go's `NewGCMWithRandomNonce`. Bundles are bounded to 8 KiB. Ciphertext and key material are excluded from Ent JSON and string representations.

`VAULT_ACTIVE_KEY` selects the writing master key. `VAULT_KEYS` contains at most four distinct versioned 32-byte keys, supplied by the deployment secret manager. Keys must differ from authentication and proxy keys. Local setup generates an independent key and preserves it on subsequent runs. Never regenerate a production key as a deployment default: losing a required version makes its bundles unreadable.

A caller must register a policy that checks resource ownership, commercial state, fulfillment mode, assignment, and lifecycle inside the same database transaction. Nil policies are rejected; the maintenance worker uses an explicit deny-all policy for interactive operations. Tests use a qualification policy against real isolated paid-order fixtures; this is not a production authorization policy or a way to mark a real order paid.

Writes are owner-only with an HMAC idempotency digest, expected version, and explicit future expiry of at most 30 days. The resource policy must impose the appropriate shorter business lifetime. Staff reveals require live account/session validation, role authorization, recent primary verification, and recent authenticator verification. Plaintext leaves the store only after its access audit commits. Denied access, corrupt ciphertext, unavailable keys, or audit failures return no plaintext. Callers must bound response lifetimes and clear plaintext byte buffers after use; Go memory management does not guarantee erasure of every historical memory copy.

Replacement, revocation, rotation, and expiry use version checks. Expiry cleanup runs in bounded minute batches; expiry itself immediately denies reveals even before cleanup runs. Revocation and expiry clear live payload and wrapped-key columns atomically with their audits. Database backups require their own approved retention and restore policy; clearing a live row does not erase historical backups.

Rotation rewraps the data key without decrypting the payload. An owner with recent verification of both factors and a resource policy can rotate a bundle. No public rotation route or bulk operational command is provided by this foundation. A deployment must retain older keys until active bundles and retained backups no longer need them, verify remaining version references, and rehearse restore before retiring keys. The later operational phase owns that workflow.

Integration qualification covers owner/resource isolation, unpaid denial, unassigned boosters, suspension, stale primary and second factors, private idempotency, concurrent replacement, corrupt ciphertext, audit rollback, live expiry, explicit revocation, and master-key rotation. Full production handoff and retention qualification remain dependent on P08, P09, and P12.
