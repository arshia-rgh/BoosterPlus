# Paid boosting fulfillment

The P08 execution stage introduces explicit SQL migration 12 and separate execution/access revisions. Administrators initialize a paid order by assigning active MFA-enabled staff. All reads and mutations recheck live session, role, payment contract, resource ownership and assignment. There is no production payment override; browser and integration tests seed synthetic settled contracts only in isolated test databases.

A published service can declare a fixed play-on-account mode, fixed play-together mode, or an explicit mapping of two required form choices. The field must be available before checkout; labels and field names never imply permission. Missing historical policies keep their orders readable but block initialization. The release also declares which ordinary fields are shared with an assigned booster. Customer form previews show this sharing scope. Booster responses omit customer IDs, email, commercial totals, coupons, and unshared answers.

Customer handoff accepts only configured fulfillment-stage fields, validating them against immutable purchased choices. It cannot revise paid selections. Temporary game access is a separate encrypted vault operation, available only for account mode. An explicit expiry makes write retries stable and must fit both the service policy and the vault's 30-day maximum. Writes bind the observed work version and use private idempotency. Staff reveals require recent primary and authenticator verification, current assignment or administrative authority, and an audit committed before plaintext is returned. The browser keeps revealed text only in memory and hides it after 30 seconds or focus loss. No game credentials enter ordinary events or notifications.

Reassignment requires recent administrator factors, invalidates the stored game secret, advances the access revision, and places work on hold. Customers are told to change their game password and submit fresh access. General progress revisions do not reset the credential-entry component. Reassignment, completion, route departure, or an access-denial response remove the relevant sensitive UI. Previously read information cannot be retroactively erased.

Execution uses queued, in-progress and on-hold states. Starting requires valid ordinary handoff and, in account mode, unexpired game access. Assigned boosters update progress and submit completion; only administrators approve final completion or return it for more work. Completion clears live game credentials and releases the package capacity hold in the same audited transaction. Customer-visible events and reference-only notification jobs are atomic with changes. Admin overrides of current estimated start/finish require a reason and preserve the accepted commercial agreement.

The current execution stage does not yet provide calendar bookings, staff availability/tags, assignment-aware proof uploads or explicit booster conversation sharing. It does not cancel/refund paid orders or resolve disputes. Those remain P08/P07 work, together with the P07 provider integration. No unspecified win-rate, no-show, refund, or settlement terms are invented. Existing customer/admin support remains private and is not automatically shared with boosters.

Frontend routes include the customer/admin order panels and the assigned-work queue/detail. Every mutation uses observed versions; stale responses require refresh. Controls disable while refresh is in flight so edits cannot race an outdated execution form. Assigned-order reads are polled and all actions enforce server authorization independently.
