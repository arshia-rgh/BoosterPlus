# Limited-package availability alerts

This P10 stage implements explicit subscriptions for published fixed-package variants with a declared capacity limit. Unique-account criteria alerts still depend on the commercial inventory workflow. No subscriber receives a reservation, priority, price guarantee, eligibility promise or automatic purchase. A capacity of zero is a valid closed offering. The storefront labels configured capacity separately from places held by contracts.

## Consent and privacy

A signed-in account explicitly accepts `availability-v1` for the selected variant. This permission is separate from order/support activity email preferences. The subscription binds an HMAC fingerprint of the current verified email, rather than storing another plaintext address. Up to 50 subscriptions may be active. Management uses owned, stable-ID pages of 50 entries. Unsubscribe and reactivation require the observed version; reactivation explicitly binds the current verified address and current opening cycle.

A changed email, missing verification or suspension suppresses delivery. Management immediately labels mismatched address consent suppressed, even if no opening has yet caused the stored state to change. A later explicit reactivation renews consent. Missing/archived/paused offers close capacity; new subscriptions require an existing published limited variant. Existing subscriptions can observe a later change to unlimited capacity. Published snapshots alone supply labels and capacity; draft content is never used.

Emails contain generic text and fixed configured-origin links. The unsubscribe capability contains subscription ID, version and a scoped HMAC, carried in the URL fragment and subsequently a POST body. It is absent from ordinary request URLs/referrers, job payloads and persistent browser storage. It remains in browser URL history until navigation; it authorizes only cancellation of that specific consent version. No GET changes consent. The anonymous page first inspects the link and requires an explicit confirmation click, both through production Origin/CSRF checks and shared address rates. Responses disclose no recipient or offering identity. A stale, tampered or already-used link yields the same currentness response. Old links cannot cancel later reactivation. HMAC key rotation invalidates old links and address bindings; owners can re-consent from their account.

## SQL, events and worker behavior

Explicit SQL19 creates target, subscription and delivery tables. Ent generates queries only. Uniqueness enforces one target per game/package/variant, one subscription per account/target and one delivery per subscription/opening cycle. No startup or Ent migration runs.

Catalog publication/pause/resume/archive/restore, package reservation, retirement/cancellation/expiry through the shared retirement path, and fulfillment capacity release enqueue reference-only `availability.changed` work in the same transaction when that game has targets. Future financial/inventory capacity mutations must use the same boundary. Workers read current state; rapid closed/open intervals that finish before observation are coalesced, not reconstructed as historical stock promises.

Targets initially snapshot current capacity at cycle zero. Only an observed closed-to-open transition increments the cycle. Subscribe/reactivate first refreshes the target and starts at its current cycle, so old stock does not become a new unsolicited message. Fanout processes at most 50 eligible subscriptions per short transaction, advances their observed cycle and inserts deduplicated delivery references atomically. A reference-only durable continuation handles the next page. Reconciliation also processes unfinished fanout, making progress even if a continuation failed.

The worker reconciles at most 50 targets each minute, retaining its cursor across passes. A failed individual target does not starve later targets; the next complete sweep retries it. Full event processing and explicit reconciliation traverse bounded pages. At large target counts, periodic repair latency grows with the number of pages; ordinary change jobs remain the prompt path. Transactions serialize through the existing identity/domain authorization fence under READ COMMITTED. There is no external I/O inside that fence. Queue leases and retry fencing remain unchanged; staff can inspect/retry the new known job kinds through audited recovery.

Immediately before SMTP, delivery rereads consent/version/address, verified unsuspended identity, current cycle and live public capacity. Pending mail older than 24 hours is suppressed as stale operational information. Delivery outcome is persisted without reviving consent. SMTP remains at least once: ambiguous acceptance may duplicate mail, and a send already accepted or in flight cannot be recalled after unsubscribe. Runtime SMTP/provider failures are generic; addresses and tokens do not enter logs/events. This is not a general marketing mailing list.

## Qualification and limits

Integration tests cover initial availability, cycles, reservation release, catalog states, ownership, CAS concurrency, mandatory audit rollback, consent quota and pagination, stale email visibility/reactivation, signed-link tampering/replay, anonymous CSRF/strict JSON, SMTP retry suppression, stale delivery, multi-page fanout/reconciliation and safe reference payloads. Real browser journeys exercise opt-in, management, a capacity-opening email, anonymous link confirmation, replay and reactivation on desktop/mobile with accessibility checks.

Local TiDB standalone tests do not replace production-equivalent TiKV query/load qualification. Live sender reputation, email link rewriting by a chosen provider, delivery policy, deployment secrets and production retention requirements remain release qualification inputs. Account-criteria alerts, account-listing favorites and account-purchase reviews remain tied to inventory/commerce. This stage does not complete all of P10 or establish production readiness.
