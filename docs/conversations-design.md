# P06 conversations and notification design

Conversation storage is private and durable. Order conversations are unique per order; authenticated pre-sales threads exist without an order. The customer owns the conversation. Administrators use explicit administrative endpoints; boosters have no access until assignment/sharing rules are implemented in P08. Linking a pre-sales conversation to an order checks the same customer, preserves the original thread, and records an audit event.

Messages are immutable, bounded plain text with a sender-scoped idempotency key and keyed request digest. Administrative notes are stored separately by visibility. Customer APIs, unread cursors, update timestamps, and change streams use a separate public sequence, so an internal note never appears in customer payloads or changes customer unread counts. Staff replies expose a configured alias or the generic support label; private staff identifiers remain in administrative records.

Short mutations use the existing TiDB READ COMMITTED security fence and recheck active sessions and roles. Conversations have open/waiting/resolved states and optional staff assignment. State/assignment/link mutations require an observed administrative revision. Customer sends reopen resolved threads and place the conversation in the staff queue. Staff replies mark it waiting for the customer; internal notes do not change the customer-facing state.

Clients page persisted messages and use server-sent events carrying only a change cursor as a refresh hint. Streams recheck live authority, expire promptly, and support reconnect/backfill. Polling remains a fallback. Event hints never contain text, email addresses, private file links, or secret material.

Notifications are private records and durable reference-only queue jobs created in the same transaction as the triggering reply. Email contains a generic activity notice and a fixed-origin link, not chat content. Current user preferences and suspension are checked at delivery time. Staff replies notify the customer; customer replies notify the assigned staff member when one is assigned. Unassigned conversations remain in the staff inbox without broadcasting email to all staff. Failed delivery retries through the existing fenced queue. SMTP is at least once: an ambiguous failure after SMTP accepts a message can cause a duplicate email; the application notification itself is deduplicated. No claim of exactly-once external delivery is made.

Secure file processing and secret storage complete the next P06 stage. Uploads stay unavailable until ownership-aware intents, quarantine, scanning, sanitized image processing, private access, quotas, and cleanup are implemented and verified. The integration will follow the [official AWS SDK checksum guidance](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/s3-checksums.html) and [ClamAV streaming protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html); scanner sockets must stay on a trusted private transport. Referenced credentials belong in the later encrypted secret workflow, not message text.
