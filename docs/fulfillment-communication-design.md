# Shared booster coordination and proof

SQL migration 14 extends private conversations with a distinct fulfillment purpose, unique fulfillment-order reference, explicit booster-sharing flag and immutable message purpose. The existing order-support conversation and pre-sales history remain separate. All SQL changes run through the Cobra migration CLI; Ent generates queries only.

An administrator with recent primary and authenticator verification can open a coordination conversation for a paid, active, assigned order. The operation checks the observed work version and creates at most one thread under the identity transaction fence. Repeating an accepted create returns the same authorized thread. Administrators can pause/resume booster sharing using the current thread revision and recent verification of both factors. Creating or changing sharing has an atomic audit record; neither action grants a role or changes private support ownership.

Customer owners retain their private history. Explicit administrator routes retain administrative access. Other callers may read this thread only when it is marked shared and they are its currently assigned, active, MFA-verified staff member on an active paid order. Ordinary order/presales threads remain owner-only outside administrator routes. This resource rule is shared by conversations and private media. The booster portal receives a direct authorized coordination link from the assigned fulfillment; it does not gain an unrestricted support inbox or customer commercial data.

Shared messages use the existing public sequence and personal read marker, which excludes internal notes. Boosters receive aliases and generic staff roles, without sender IDs or internal sequence numbers. Administrator-only notes and images remain excluded, even inside a shared thread. Reassignment, sharing pause, role/session revocation or suspension stops new reads, writes, signed downloads and live subscriptions. Already viewed information cannot be recalled. The frontend clears unavailable thread content after an authorization failure and refreshes on stream failure; normal polling remains available.

Only an administrator or currently assigned booster can publish a proof message in the coordination scope. At least one ready image is required. Images pass existing quarantine, real antivirus scanning, dimension/size bounds, normalization and integrity checks. Binding requires the same conversation, uploader and public audience; internal images cannot be downgraded into public proof. Proof is an immutable message purpose, with an atomic order-timeline event and audit. Idempotent retries do not bind an image or append the proof timeline twice. Proof publication does not itself approve completion or change an accepted price.

Private downloads remain short-lived and session-bound, with live membership checks before and after storage access. Customer owners can view published proof through their conversation. Boosters lose image access when sharing or the active assignment no longer permits it. Credentials remain in the separate temporary game-access workflow.

Customer, support and assigned-booster notices contain only durable references and generic fixed-origin email links. Booster notification delivery rechecks current sharing, staff authority, payment and assignment. Reassignment or sharing pause suppresses queued booster delivery. SMTP retains the documented at-least-once limitations. Internal notes trigger no customer/booster activity notice.

Qualification covers private support separation, shared/public versus internal history, scanned proof, attempted internal-image downgrade, concurrent retries, fresh factors, audit rollback, reassignment/download revocation and real SSE closure on sharing pause. Desktop/mobile journeys cover explicit sharing, coordination, scanned proof publication, customer download and pause/resume access behavior. Full phase and production qualification remain tracked separately.
