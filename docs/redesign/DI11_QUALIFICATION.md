## DI11A — private product authoring

Scope: explicit SQL migration 34 and Ent query mappings; separate admin-authorized shop API; product listing/search/game/state filters; private draft creation; persistent editor sections; bounded variants, exact minor-unit prices, recipient-field declarations and explicit commercial terms; saved preview and reviewed immutable publication; pause/resume/archive/restore; versioned capacity with reserved/committed floors; paginated immutable publication history. Every mutation audits within the same authorization-fenced transaction. Restoration never automatically reactivates a public product, and publication never invents stock.

Staff edits stay inside `/admin/shop/:id`, retain the product/game/revision identity and return to the same filtered list. Ordinary draft and stock edits survive local sections, and leaving requires an explicit discard choice. Stock writes also block departure while in flight. A newer revision cannot silently overwrite edits; denied access clears private content, while transport failures hide and lock the editor without destroying ordinary drafts. Named validation links select the relevant local section and focus the associated field. Publication and capacity changes require explicit review; sensitive operations retain recent first- and second-factor verification.

No commercial products, prices, regional promises or delivery terms were seeded. Automated examples are isolated fixtures. Artwork must be an approved local catalog asset with alternative text and provenance. The declared recipient schema permits only ordinary delivery identifiers, never credential fields; actual private recipient capture belongs to DI11B.

## DI11B1 — reservation foundation (in verification)

Explicit SQL migration 35 adds a deliberate shop order snapshot/reference, quantity reservations and a separate private recipient table. Ent generates queries only. Recipient values are ordinary delivery identifiers, not credentials; no recipient API or public checkout is registered in this increment. Export/erasure and authorized masked/recent-factor views are required before real recipient capture is activated.

Publication maintains a searchable current-variant projection while preserving reserved/committed units for retired variants. Reusing a published key for different region/platform/server is rejected in both saved preview and publication; use a new key so prior inventory obligations retain their identity. Migration 35 deliberately initializes legacy authoring-only projections disabled: an existing DI11A product must be reviewed and republished to populate its current variant projection before later public activation. There were no public shop purchases in DI11A, and this migration does not invent capacity or backfill draft data as a public release.

Internal transaction hooks move reserved units to paid commitments once, reject allocation after release, extend only unexpired reservations to the accepted invoice deadline, and never restock automatically on cancellation/refund. They still require the payment layer's authenticated evidence/contract fence and are **not yet connected to live checkout or reconciliation**. The next increment must wire and qualify those paths; these isolated hook tests are not end-to-end payment qualification.

Boost fulfillment now explicitly admits only custom/package boost kinds. A test gives a shop record a deliberately invalid legacy booster assignment in an isolated database and verifies that read, assignment and queue boundaries still reject it. Generic boost creation also rejects the shop kind.
