## Reproducibility and attempt boundaries

- The initial account-commerce run stopped after observing14, because the next control was concealed. Its replacement uses the existing access-recovery button. The replacement then stopped on a test selector treating a disclosure summary as a button; the subsequent account-case-refund bundle performs the actual case/appeal/refund actions.
- First quote run changed a server prerequisite without refreshing the owned order before opening Progress. The view correctly retained its previous unpaid snapshot. The completed round2 explicitly refreshes first; this setup error is not a product failure.
- First shop run expected a nonexistent button label. Completed round2 reloads the now-seeded payment state and continues. Prior successful reserve checkpoints remain evidence, but the interrupted run is not an end-to-end pass.
- First reschedule script used `calendar_conflict`, which is not the endpoint's actual error code. Round2 repeats the branch with backend `fulfillment_conflict`; only round2 establishes exact conflict-copy coverage.
- Handoff validation was repeated with consistent in-progress order/delivered bundle state; round2 is authoritative.
- No unknown or wildcard “success” API fallback was added. UI mutations require exact expected payloads. Source snapshots and earlier failed attempts are retained.
