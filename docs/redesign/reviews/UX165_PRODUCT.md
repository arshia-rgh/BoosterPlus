## B-O02 — calendar decision

The observed 320px UTC calendar makes the operator consider a “repeated clock hour” for both start and end even though UTC has no daylight-saving ambiguity. Each date/time and occurrence is also read back immediately after its editable control, while multiple surrounding descriptions repeat availability-versus-booking guidance. The task succeeds and there is no horizontal overflow, so this is not a scheduling-function failure. The issue is unnecessary decision work and vertical density during a simple availability task.

**Approved minimal scope for this round:**

1. Hide the repeated-hour selector only when the effective time zone is exactly `UTC`. Keep the selected zone visible near the date/time group. Do not invent client-side DST calculations or infer every alias/fixed-offset zone.
2. Keep non-UTC repeated-hour selectors visible. Do not collapse them behind a new disclosure yet: the server can return a generic `time` issue rather than an occurrence-field path, so the existing first-invalid helper alone cannot guarantee the correcting control is revealed. A future contextual disclosure needs explicit generic-time error opening and focused regression coverage.
3. Remove the immediately repeated date/occurrence readbacks where the same values are already in labeled inputs. Preserve an unambiguous zone and the distinct reviewed/published window summary.
4. Remove the redundant *visible* outer “Calendar controls” legend; retain an accessible group name and disabled-state semantics. Keep meaningful sections such as Staffing profile, Publish availability and Published availability.
5. State the 15-minute–12-hour duration, 90-day horizon and finite weekly repetition constraints once where dates are entered/reviewed. Keep one clear notice that publishing availability does not confirm a customer session. Retain conflict/confirmed-session-removal guidance when relevant.

**Implementation caveat discovered in source:** `bookings.tsx` keeps the editable `zone` separately from `start.zone`/`end.zone`; submission uses the separate effective zone. If `TimeInput` conditionally hides selectors based on `value.zone`, its booking callers must pass the effective current zone too. Otherwise changing UTC to Europe/London would wrongly leave occurrence controls hidden. Check the reverse transition and any preselected occurrence so input visibility and the submitted effective zone remain consistent. The backend currently accepts a valid unambiguous time irrespective of an occurrence selection; do not invent a new rejection rule. This is a prospective regression risk from the proposed visibility change, not a reported current-user failure.

Root subsequently confirmed implementation of this minimal decision, including the effective booking-zone fix and focused regressions. This is an implementation report, not my independent execution receipt. Required rendered proof: UTC at 320/390/desktop; blank dates and invalid duration; non-UTC normal time and ambiguous/nonexistent clock-change responses; calendar profile zone change; booking UTC→Europe/London→UTC; reviewed weekly date list; fresh focus/keyboard and no clipping. Existing authoritative backend DST/conflict rules stay unchanged. Designer decides exact spacing after observing the rebuilt screen; reducing height alone is not acceptance.
